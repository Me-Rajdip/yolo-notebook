0. Why am I studying this?

Object detection = find what is in an image AND where it is (a box around it).

YOLO's whole trick: do it in one pass through one network, instead of a multi-stage pipeline.

Before I touch any version, I need two building blocks solid:
bounding boxes and IoU.
Everything else is built on these.

p. 1

1. Bounding boxes — two ways to write one

  • Corner format: (x₁, y₁, x₂, y₂) — top-left corner, bottom-right corner.
  • Center format: (x, y, w, h) — center point, then width and height.

YOLO uses center format.

Note to self: why? The network predicts a center point relative to a grid cell — that only makes sense in center format. Corner format would force it to know absolute edges, which don't align nicely with a grid.
p. 2

2. IoU (Intersection over Union)

the one formula I must never forget

IoU(A, B) = Area(A ∩ B)Area(A ∪ B)
  • Numerator = overlapping region.
  • Denominator = total space covered by both boxes combined.
  • Range: 0 (no overlap) to 1 (identical boxes).

Trick for the union, since I never measure it directly:

Area(A ∪ B) = Area(A) + Area(B) − Area(A ∩ B)

(reasoning: if I just add both areas, the overlapping part got counted twice, so subtract it once.)

Worked example — by hand

Box A: x ∈ [100, 200], y ∈ [100, 200] → area = 100 × 100 = 10,000

Box B: x ∈ [150, 250], y ∈ [120, 220] → area = 10,000

Overlap region:

  • x-overlap: from 150 to 200 → width 50
  • y-overlap: from 120 to 200 → height 80
  • Intersection = 50 × 80 = 4,000
Union = 10,000 + 10,000 − 4,000 = 16,000
IoU = 4,00016,000 = 0.25

Rule of thumb: IoU ≥ 0.5 is usually considered "a correct detection."

✓ Check myself: if the two boxes were identical, intersection = union, IoU = 1. Makes sense.

p. 3

3. YOLOv1 (2015) — the original idea

Paper: "You Only Look Once: Unified, Real-Time Object Detection" — Redmon, Divvala, Girshick, Farhadi.

3.1 The core rule

Divide the image into an S×S grid. Whichever cell contains the center of an object is responsible for detecting that object.

YOLOv1 specifics: S = 7, input image 448×448, so each cell = 448 / 7 = 64 pixels.

Each cell predicts:

  • B = 2 bounding boxes (each with 5 numbers)
  • C = 20 class probabilities (PASCAL VOC has 20 classes) — shared across both boxes in that cell
This is a real limitation: one cell = one class guess, no matter how many boxes. Two overlapping objects of different classes centered in the same cell → one gets missed. Explains a weakness later.

3.2 Encoding a box as numbers

Raw pixel numbers (like 300, 224) are big and awkward for a neural net to learn. So normalize:

  • (x, y) = center, relative to its own cell, in [0, 1]
  • (w, h) = size, relative to whole image, in [0, 1]

Worked example (redo this myself)

Dog box: center at pixel (300, 200), width 160, height 224.

Which cell? ⌊300/64⌋ = 4 (column), ⌊200/64⌋ = 3 (row).
Cell (row 3, col 4) starts at pixel (256, 192).

x = 300 − 25664 = 0.6875    y = 200 − 19264 = 0.125
w = 160448 = 0.3571    h = 224448 = 0.5

Decode check: (4 + 0.6875) × 64 = 300 ✓ — round trip works.

3.3 The 5th number: confidence

c = Pr(Object) × IoUtruthpred
  • No object in the cell → target is 0.
  • There IS an object → target is the actual IoU of my predicted box with the truth.

This is clever: a badly-placed box, even in the right cell, gets punished with a low confidence target. The model is forced to be honest about its own box quality, not just "yes/no there's something here."

3.4 Class probabilities

Each cell also predicts Pr(Classi | Object) — for the 20 classes. At test time:

Pr(Classi | Object) × Pr(Object) × IoU = Pr(Classi) × IoU

Example: cell says "dog" with prob 0.9, box confidence 0.7 → final dog score = 0.9 × 0.7 = 0.63.

3.5 Output size — count it myself

Each cell: B·5 + C = 2×5 + 20 = 30 numbers.

Whole grid: 7 × 7 × 30 = 1,470 numbers.

That's it. That's the entire output of YOLOv1 for one image — a 7×7×30 tensor.

3.6 The network (just the shape)

  • 24 conv layers + 2 fully connected layers, alternating 1×1 (channel squeeze) and 3×3 (spatial) convs.
  • Activation: leaky ReLU
φ(x) = x   if x > 0   |   0.1x   otherwise
  • Image shrinks: 448 → 224 → 112 → 56 → 28 → 14 → 7. That's 6 halvings → 2⁶ = 64 → exactly why a 448px image gives a 7×7 grid. ✓ Connects two things I thought were unrelated.
  • Final feature map 7×7×1024 → flatten to 50,176 → FC 4096 → FC 1470 → reshape to 7×7×30.
First FC layer alone ≈ 205 million weights. Most of the model's size lives there (later versions get rid of this).

3.7 The loss function — slow down here

Naive idea: sum-squared error everywhere. The paper patches each problem with it.

Notation:

  • hat = predicted, no hat = ground truth
  • 𝟙objij = 1 if box j in cell i is "responsible" (object's center is in cell i AND this box has the best IoU of the cell's boxes)
  • 𝟙noobjij = 1 − 𝟙objij
ℒ = λcoord Σi,j 𝟙objij [ (xi − x̂i)² + (yi − ŷi)² ]
   + λcoord Σi,j 𝟙objij [ (√wi − √ŵi)² + (√hi − √ĥi)² ]
   + Σi,j 𝟙objij (Ci − Ĉi)²
   + λnoobj Σi,j 𝟙noobjij (Ci − Ĉi)²
   + Σi 𝟙obji Σc (pi(c) − p̂i(c))²

Five parts. Each in my own words, like I'd explain to a friend:

  1. Center error. How far off is my predicted (x, y) from the truth. Only counted for the responsible box.
  2. Size error, but with square roots — why?? (see below)
  3. Confidence error (object present). Target = actual IoU.
  4. Confidence error (no object). Target = 0. Why down-weighted (λnoobj = 0.5)? Most of the 49 cells are empty in a typical photo. If I don't down-weight, the huge number of "nothing here" cells could dominate training and the model just learns to always predict "empty." Classic class-imbalance problem, solved by weighting.
  5. Classification error. Squared error on class probs, only where an object exists.

Weights used: λcoord = 5 (care a lot about location) and λnoobj = 0.5 (care less about empty background).

Why square roots on size?

This one confused me at first.

  • Big box: true w = 0.5, predicted 0.45 → error 0.05
  • Small box: true w = 0.1, predicted 0.05 → error 0.05 (same absolute error!)
  • Plain squared error treats both the same: 0.05² = 0.0025.
  • But 0.05 off on a small box is proportionally way worse (half its size!) than on a big box.
box√ differencesquared
Big√0.5 − √0.45 = 0.7071 − 0.6708 = 0.03630.0013
Small√0.1 − √0.05 = 0.3162 − 0.2236 = 0.09260.0086

Small-box mistake now costs ~6.5× more.

Why does sqrt do this? The slope of √w is 12√w — steeper when w is small. Same input error → bigger output change when w is small. Exactly the property I want.

3.8 Full worked example of the loss

Ground truth (my dog): x = 0.6875, y = 0.125, w = 0.3571, h = 0.5

Prediction: x̂ = 0.60, ŷ = 0.20, ŵ = 0.30, ĥ = 0.45, confidence Ĉ = 0.60 (true IoU = 0.70)

Class pred: dog 0.8, cat 0.1 (true: dog = 1, cat = 0)

Empty-cell box predicts confidence 0.2

3.9 Inference: raw output → actual boxes

  1. Compute class-specific confidence for every one of the 7 × 7 × 2 = 98 boxes.
  2. Drop anything below a threshold (e.g. 0.25).
  3. Run Non-Max Suppression (NMS) to kill duplicates.

NMS algorithm, in my own words

  1. Sort remaining boxes (of one class) by score, highest first.
  2. Keep the top one. Delete every other box that overlaps it too much (IoU > 0.5, typically).
  3. Move to the next surviving box, repeat.

A: score 0.90, box (100, 100, 200, 200)

B: score 0.80, box (110, 105, 210, 205)

C: score 0.60, box (300, 300, 400, 400)

Keep A. Compare B vs A: overlap = 90 × 95 = 8,550. Union = 20,000 − 8,550 = 11,450. IoU = 0.747 > 0.5 → delete B (duplicate of the same dog).

Compare C vs A: no overlap → IoU = 0 → keep C (a different dog).

Final: A and C survive.

3.11 Weaknesses — my own summary

  • 1 class per cell → struggles with small/clustered objects (e.g. flock of birds)
  • No shape priors → struggles with unusual aspect ratios
  • Only 7×7 predictions → bad at small objects (too coarse)
  • Square-root trick is a patch, not a real fix — doesn't directly optimize IoU
Every later YOLO version attacks one of these four bullets. Keep as a checklist for the next sections!

4. YOLOv2 / YOLO9000 (2016–17)

fixing "no shape priors"

Key additions:

  • Batch normalization on every conv layer (better accuracy, dropped dropout)
  • Fully convolutional — no more giant FC layers. Grid now 13×13 @ 416×416 input.
  • Anchor boxes ← the big one
  • Multi-scale training — randomly resize input every few batches (320 to 608, multiples of 32)
  • New backbone: Darknet-19

4.1 Where do anchor shapes come from?

Idea: don't predict a box from nothing — predict a tweak to one of a few pre-picked "typical" shapes (anchors).

To find good anchor shapes: run k-means on all ground-truth boxes in the dataset, but with this distance:

d(box, centroid) = 1 − IoU(box, centroid)

Why not plain Euclidean distance? It would let big boxes dominate the clustering (a box 10px off but huge looks "far" in raw pixels even though its shape is basically identical). Using 1 − IoU clusters by shape, which is what matters. Paper found k = 5 anchors a good balance.

4.2 Decoding an anchor-based prediction

Network outputs raw numbers tx, ty, tw, th, to per anchor:

bx = σ(tx) + cx    by = σ(ty) + cy
bw = pw etw    bh = ph eth
Pr(Object) · IoU = σ(to)
  • (cx, cy) = cell's top-left corner (grid units)
  • (pw, ph) = the anchor's own width/height
  • σ = sigmoid, squishes anything into (0, 1)

Why sigmoid on the center? Forces the predicted center to stay inside its own cell. Without it, early predictions could fly anywhere and training gets unstable.

Why exponential on the size? (1) guarantees a positive number (no negative width!), and (2) tw = 0 ⇒ bw = pw, i.e. "no change" naturally means "just use the anchor." Predicting a multiplicative adjustment to a known shape is easier than predicting absolute size from scratch.

My own numbers

Cell (4, 3), anchor width pw = 2.0, network outputs tx = 0.2, ty = −1.0, tw = 0.3.

bx = σ(0.2) + 4 = 0.5498 + 4 = 4.5498
by = σ(−1.0) + 3 = 0.2689 + 3 = 3.2689
bw = 2.0 × e0.3 = 2.0 × 1.3499 = 2.700

Result @ VOC 2007: 76.8 mAP @ 67 FPS. Big jump from v1's 63.4.

(The "9000" part = trained jointly on detection + ImageNet classification via a label hierarchy, so it could detect way more classes than it had boxes for. Side note, not the main architectural story.)

5. YOLOv3 (2018)

fixing "bad at small objects"

Additions:

  • Deeper backbone: Darknet-53 (with residual/skip connections)
  • Three prediction scales: strides 32, 16, 8 — coarse map for big objects, fine map for small ones
  • 9 anchors total (3 per scale)
  • Independent logistic classifiers instead of one softmax (an object can have more than one label — e.g. "person" and "woman" both true — trained with binary cross-entropy)

Count the candidate boxes myself

416×416 input, COCO (80 classes). Grids: 13×13, 26×26, 52×52. Per cell: 3 anchors × (4 box + 1 obj + 80 class) = 3 × 85 = 255 channels.

(13² + 26² + 52²) × 3 = (169 + 676 + 2704) × 3 = 3549 × 3 = 10,647

vs YOLOv1's 98 candidates. ~100× more candidates → much better at catching small stuff.

Side note: Joseph Redmon (original author) stepped away from CV research around here over concerns about military applications. From v4 onward, "YOLO" is a community name, not one team's official lineage.

6. The IoU-loss family

fixing "square-root trick isn't real IoU optimization"

Plain 1 − IoU as a loss has a real flaw: if boxes don't overlap at all, IoU = 0 and the gradient is also 0 → the model gets zero signal on which direction to move. Needs fixing.

GIoU (Generalized IoU)

Draw the smallest box C that encloses both A and B:

GIoU = IoU − Area(C) − Area(A ∪ B)Area(C)

Now even non-overlapping boxes get a gradient (shrink the "wasted space" in C).

My example (A, B from section 2): enclosing box = 150 × 120 = 18,000.

GIoU = 0.25 − 18,000 − 16,00018,000 = 0.25 − 0.111 = 0.139

DIoU (Distance IoU)

Adds a penalty for how far apart the centers are:

DIoU = IoU − ρ²c²

ρ = distance between centers, c = diagonal of the enclosing box.

Centers: (150, 150) and (200, 170). ρ² = 50² + 20² = 2900. c² = 150² + 120² = 36,900.

DIoU = 0.25 − 290036,900 = 0.25 − 0.079 = 0.171

CIoU (Complete IoU)

Adds one more term for aspect ratio mismatch:

CIoU = IoU − ρ²c² − α v
v = 4π² ( arctan wgthgt − arctan wh )²    α = v(1 − IoU) + v

In my example both boxes are square (100×100), so v = 0 → CIoU = DIoU = 0.171 here.

Loss used in practice: 1 − CIoU. YOLOv4 popularized this, and it's stuck around since.

Memory hook:
IoU → GIoU (fixes zero-gradient) → DIoU (adds center-distance) → CIoU (adds shape-match).
Each one adds a term on top of the last.

7. YOLOv4 → v10 — speed run

Don't need to derive every one in depth, just know what each one changed:

  • v4 (2020) — organized tricks into "bag of freebies" (Mosaic aug, CIoU loss — free accuracy) and "bag of specials" (small architecture add-ons). CSPDarknet53 backbone. 43.5 AP @ ~65 FPS (V100).
  • v5 (2020, Ultralytics) — not a research paper, a clean PyTorch implementation. Made YOLO easy for regular developers. Huge for adoption.
  • v6 (2022, Meituan) — hardware-friendly reparameterizable blocks, industrial/edge focus.
  • v7 (2022) — E-ELAN (efficient layer aggregation), "trainable bag of freebies."
  • v8 (2023, Ultralytics) — anchor-free (!) + decoupled head (separate branch for box vs class). Becomes the base design for everything after.
  • v9 (2024) — PGI (programmable gradient info) + GELAN, aimed at not losing information in deep networks.
  • v10 (2024, Tsinghua) — first YOLO trained to give one prediction per object, i.e. NMS-free.
Checklist mentality: v8 removed anchors. v10 removed NMS. Both get carried into v11 and beyond.

8. YOLO11 (2024, Ultralytics)

the current "safe default"

Three structural changes vs v8:

  1. C3k2 block replaces C2f (backbone/neck)
  2. C2PSA (attention block) inserted after SPPF
  3. Lighter, depthwise-separable convs in the head's classification branch

8.1 C3k2 — what's a CSP block, really?

CSP = Cross-Stage Partial. Idea: split incoming channels in two. One half skips straight through untouched. The other half goes through the expensive bottleneck layers. Concatenate both halves at the end.

Why: cheaper (only half the channels do heavy work) + better gradient flow (skip path). C3k2 is a faster variant where the inner unit can switch between "light" and "heavier" versions depending on the stage — shallow layers stay cheap, deep layers get more power.

8.2 SPPF then C2PSA

seeing wider, then seeing "smarter"

SPPF (Spatial Pyramid Pooling — Fast): apply a 5×5 max-pool, then apply it again to its own output, then again. Each pass widens the effective receptive field: 5×5 → 9×9 → 13×13. Concatenate the original + all 3 pooled versions → the next layer sees multiple context sizes at once, cheaply.

C2PSA (attention): convolutions only look at a small local neighborhood. Attention lets every position ask "which other positions matter to me?"

Attention(Q, K, V) = softmax( Q Kᵀ√d ) V
  • Q = query ("what am I looking for")
  • K = key ("what do I contain")
  • V = value ("what I pass along if picked")
  • Q Kᵀ = similarity scores between every pair of positions
  • √d = scaling so scores don't blow up with dimension size
  • softmax → turns scores into weights summing to 1
  • multiply by V → blend

Tiny example myself: 2 positions, d = 2

Q = K = [ 1 0 ; 0 1 ]    V = [ 2 0 ; 0 4 ]

Q Kᵀ = I. Divide by √2: diagonal = 0.707, off-diagonal = 0.

Position 1's softmax: e0.707e0.707 + e0 = 0.670 and 0.330.

output₁ = 0.670 × (2, 0) + 0.330 × (0, 4) = (1.34, 1.32)

So position 1's new representation is a blend of both positions' values, weighted by relevance — not just its own local patch. That's the whole point: distant context helps with small/occluded objects. C2PSA does this only on the smallest feature map (cheap enough to stay real-time).

8.3 Lighter head — depthwise-separable convs

Normal 3×3 conv, 64 → 64 channels: 3×3×64×64 = 36,864 weights.

Depthwise-separable: per-channel 3×3 (3×3×64 = 576) + 1×1 channel mix (64×64 = 4,096) = 4,672 weights.

≈ 8× fewer weights, similar result. Only used in the classification branch of the head.

8.4 Anchor-free head — how does it predict a box with no anchors?

Every position on each feature map (stride 8, 16, 32) predicts distances to the 4 box edges from that point: left, top, right, bottom.

At 640×640 input: grids are 80×80, 40×40, 20×20.

6,400 + 1,600 + 400 = 8,400 candidate predictions total

My own worked example

Stride 16, position (col 20, row 10) → pixel center (20.5×16, 10.5×16) = (328, 168).

Predicted distances (stride units): l = 2, t = 3, r = 4, b = 1 → pixels: 32, 48, 64, 16.

Box: (328 − 32, 168 − 48) to (328 + 64, 168 + 16) = (296, 120) to (392, 184) → 96 wide, 64 tall.

DFL (Distribution Focal Loss)

Instead of predicting one number for each distance, predict a small probability distribution over possible bin values, then take the expected value.

Bins 0–3 with probs (0.1, 0.2, 0.6, 0.1) → expected distance = 0(0.1) + 1(0.2) + 2(0.6) + 3(0.1) = 1.7.

YOLO26 removes DFL — remember for comparison later!

8.5 Task-aligned assignment

which candidate "owns" which object during training?

With 8,400 candidates and only a handful of real objects, I need a rule for who trains on what. Score:

t = sα · uβ

s = predicted score for the correct class, u = box IoU with truth. Typical α = 0.5, β = 6.

candidatesucalculationt
10.80.70.80.5 × 0.7⁶ = 0.894 × 0.1180.105
20.90.40.949 × 0.00410.0039

Even though candidate 2 has a higher class score, its much worse IoU tanks its total because of the high exponent (β = 6) on u. Lesson: this assigner cares much more about accurate localization than class confidence alone.

9. YOLO12, YOLO13, YOLO26

quick notes

  • YOLO12 (2025) — heavier attention (area attention + R-ELAN). ~40.5 mAP nano, ~1.1 pt above YOLO11-n. Downside noted by Ultralytics itself: training instability, higher memory, slower CPU — recommended for research/benchmarking, not production.
  • YOLO13 (2025, iMoonLab) — hypergraphs: one "edge" can connect many nodes at once (vs normal attention which is pairwise). Claimed +3.0 mAP over YOLO11-n, +1.5 over YOLO12-n.
  • YOLO26 (Jan 2026, Ultralytics) — direction changes back toward simplicity + deployment: native NMS-free, removes DFL entirely, new optimizer (MuSGD), progressive loss, STAL label assignment. Up to 43% faster CPU inference than YOLO11.

Big-picture note to self: YOLO26 closes a loop — v1 killed the region-proposal pipeline, v8 killed anchors, v10 killed NMS's necessity, and now v26 kills NMS and DFL as standard parts of the head. The whole family's story is "remove pipeline stages," not just "add more layers."

11. Metrics — precision, recall, mAP

so the table above actually means something to me

Precision = TPTP + FP     Recall = TPTP + FN
  • TP = correct detection (IoU past threshold + right class)
  • FP = wrong detection
  • FN = missed real object

My example

3 real dogs, 5 detections ranked by confidence: TP, TP, FP, TP, FP.

RankResultPrecisionRecall
1TP1.000.33
2TP1.000.67
3FP0.670.67
4TP0.751.00
5FP0.601.00

AP = area under the precision-recall curve (best precision at each recall level or above):

AP = 0.333(1.00) + 0.333(1.00) + 0.333(0.75) = 0.917

mAP = average AP across all classes.

  • mAP@0.5 = one IoU threshold.
  • mAP@0.5:0.95 = average over 10 thresholds (0.5 to 0.95) — much stricter, rewards tight boxes.

That's why COCO numbers "look lower" than VOC numbers for similar-quality models.

for actually running this myself

pip install ultralytics
# n/s/m/l/x sizes from ultralytics import YOLO model = YOLO("yolo11n.pt") results = model("image.jpg")

Label format (one .txt per image, one line per box):

class_id x_center y_center width height # all normalized 0-1

— literally the same normalization I derived by hand in section 3.2.

model.train(data="data.yaml", epochs=100, imgsz=640) model.val() model.export(format="onnx")

Reminders to self

  • Start from pretrained weights, don't train from scratch (transfer learning).
  • Label quality > model size.
  • Watch validation mAP, not just training loss, to catch overfitting.
  • Small objects need bigger imgsz.
  • Confidence threshold is a precision/recall dial — pick it for the actual use case.

13. One-paragraph summary

can I explain this without notes?

YOLOv1 divided an image into a grid and made each cell responsible for objects centered in it, predicting boxes and classes in one pass instead of a slow multi-stage pipeline. v2 added anchor box priors found via k-means. v3 added multiple prediction scales to catch small objects. Along the way, IoU-based losses (GIoU → DIoU → CIoU) replaced the awkward square-root size loss. v4–v7 refined training tricks and efficiency. v8 removed anchors entirely and split the head into box/class branches. v9–v10 improved gradient flow and made NMS optional. v11 added CSP-style C3k2 blocks and a small attention module (C2PSA) for better context, staying anchor-free and needing NMS. v12–v13 pushed further into attention/hypergraphs for accuracy at some efficiency cost. v26 went back to simplicity: NMS-free and DFL-free by design, tuned for edge devices. The whole story, version after version, is fewer separate stages and more of the work happening inside one clean forward pass.
